Every filing is checked against a versioned rule set, and coded fields against versioned value lists. The version in force on a date is the newest published one effective by then, and every submission and run records the versions it was checked against. A published version never changes: a change is a new version with the date it takes effect and the reason.

Filing specifications

Filing specifications (open to everyone) say what each kind of filing holds: its tables, the fields of each, which are required, each field's type, value list and definition, the rules about it in words, and the built-in checks. The CPUC publishes each specification in named versions, and each filing on the calendar is set up with one: its upload page links the version under "Before you upload", and its findings name the version the file was checked under.

  • Download a version's upload template (a workbook, or a .zip of pipe-delimited files), every field and rule as a workbook, or the whole version as JSON with a JSON Schema for each table. Systems can read the same JSON from the API at /api/v1/specifications/.
  • Compare two versions to see the tables, fields, rules and checks that changed.
  • A filing keeps the version it was set up with when a newer one is published; a later filing set takes the newer one.

For filers

  1. Read the rules your filing will be checked against on Validation rules (signed in). Each rule has its ID, severity (reject or warning), the field it checks, the message you see and how to fix it.
  2. Check a file before you file it: it runs a filing's rules on one table of your file, exactly as the upload does, and keeps nothing. Check against the rules in force, or a later version that has not taken effect yet.
  3. The upload also runs checks that need the whole filing (its other tables, earlier confirmations, eTRM's values for deemed claims), so a file that passes the check can still get findings on upload. Those checks are listed, with their IDs, severity and message, on Built-in checks.
  4. The codes a field may hold are on Value lists. A code is accepted for claim years from its start year to its end year; a retired code keeps its row with an end year and is never deleted.

For the CPUC staff who keep them

  • Rules change without a code change. Start a new version of a published rule set with its effective date and reason, then add, change or take out rules in the draft and publish it. A changed test gives a rule a new ID that names the rule it replaces.
  • Compare two rule sets before a new version takes effect, and announce it in a release note.
  • A value list's draft starts as a copy of its newest version. Add codes, retire a code by giving its last claim year, or reinstate it by clearing that year; many codes at once from a CSV.
  • A field in the data dictionary is retired, never deleted, after usage, audience and regulatory reviews. Every dictionary version's changes are on the specification change log.
